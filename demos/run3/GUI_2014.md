# The 2014 edition's GUI — what to match, and where it is written down

This is the reference for the port's menus/HUD. It is decoded from the **2014**
build, `swf_orig/runIII.swf`, because that is the edition the port is measured
against. Nothing here is inferred from the port.

---

## 0. Read the right tree

| tree | came from | what it is |
|---|---|---|
| `swf_orig/decomp/runIII/scripts/` | `swf_orig/runIII.swf` | **the 2014 edition** — the ground truth |
| `src/`, `readable_src/` | `Run3.swf_Decompiler.com.zip` at the repo root, which is byte-identical to `swf_orig/run3-adobeflash.swf` (and to `~/Downloads/Run3.swf`) | a **later** build |

`bake_src.py` states this in its header: `src/` is decompiled from
`Run3.swf_Decompiler.com.zip`. That zip is the *adobeflash* SWF, not `runIII`.
So `readable_src/` — the tree the cutscene / layout / level decodes were read
from — is the **later** build, and any GUI read from it has to be re-checked
against `runIII` before it is trusted.

The two menus are not the same screen, and the difference is not cosmetic:

| | 2014 (`runIII`) | later (`src/`) |
|---|---|---|
| menu class | `com/player03/run3/menu/§-__-_--__-_-§.as` | `com/player03/run3/menu/§;!G§.as` |
| placement | **absolute pixel writes** (`x = …`, `y = …`) | the `com.player03.layout` gravity/anchor engine |
| top-right | `menu/CreditsIcon.png` | `menu/GearIcon.png` |
| cutscene icon | does not exist | `menu/CutsceneIcon.png` |
| `menu/QualityIcon.png` | does not exist | present |

So the 2014 menu is *much* easier to reproduce than the later one: it needs no
layout engine, just the numbers below.

## 1. ScaledAssets — how the 2014 turns design units into pixels

`haxeutils/display/ScaledAssets.as` (both builds; the 2014's is identical in
substance):

```
scaleX, scaleY                     // the design scale, set once at boot
drawing a bitmap:  scaleX * 2      // Bitmap.scaleX = 2*scaleX, scaleY = 2*scaleY
getWidth( v)  ->  v * scaleX       // a horizontal distance
getHeight(v)  ->  v * scaleY       // a vertical distance
font size (v) ->  v * scaleY
assets are addressed as "img/" + name, e.g. "img/menu/Run3.png"
```

**Note the ×2.** A bitmap is drawn at *twice* the design scale, while a
distance is drawn at the design scale. That is why the menu constants look small
(90, 40, 30, 25, 20) next to a 642-pixel-wide title: the title covers `642*2*sx`
of screen while the margin is `90*sx`.

The design box the port already uses for the map is the same one:
`k = min(BASE_W/3000, BASE_H/2000)`, `sx = sy = k`. Gaps and the map's rule come
from the same `ScaledAssets` instance, so the menu must use the same `k`.

At the port's base box (`BASE_W 960`, `BASE_H 720`): `k = 0.32`, `2k = 0.64`.

## 2. The 2014 main menu, element by element

From `com/player03/run3/menu/§-__-_--__-_-§.as`, `create()` and `reset()`.
`sw`/`sh` are `stageWidth`/`stageHeight`. `sx`/`sy` are the ScaledAssets scales.

Created on entry, in this order:

| element | asset | position |
|---|---|---|
| title | `menu/Run3.png` (642×212) | `x = (sw − 642·2sx)/2`, `y = 90·sx` |
| links bar `§--___--_--§` | — | `x = 2·(20·sx)`, `y = 20·sx` |
| credits / options | `menu/CreditsIcon.png` (123×123) | `x = sw − w − 20·sx`, `y = 20·sx` |

```
playY = charSelect.y + charSelect.<box>.height + 90·sx
```

`assets/images/menu_*.png` are the same bytes: the 2014 doesn't have a
`QualityIcon`, a `CutsceneIcon` or a `GearIcon`, and the port's
`menu_qualityicon.png` is therefore from the later build (see §0).

Evaluated at 960×720 (`k = 0.32`, so `2k = 0.64`, margins `20·sx = 6.4`,
`25·sx = 8`):

## 3. What the port draws now (implemented)

`render_menu()` in `render.c` is the §2 screen: the 2014's own bitmaps, at the
2014's own positions. The pieces, and where each lives:

| piece | file |
|---|---|
| the bitmaps | `levels/bake_menu.py` → `levels/menu_assets.h` (`static const uint32_t name[]`), following `levels/bake_map.py` → `map_assets.h` |
| their native sizes | the same bake → `levels/menu_metrics.h` |
| the layout (the ONE description) | `run3_menu_rect` / `run3_menu_char_rect` / `run3_menu_icon_w` in `run3.c` |
| the drawing | `draw_items` / `draw_grid` in `render.c` |
| text metrics | `render_menu_text_w` / `render_menu_text_h` in `render.c`, which `run3_menu_rect` builds its boxes from |
| hit-testing | `run3_menu_hover` / `run3_menu_click`, testing the same rects |

The rule is stated once in `run3.h` above `MENU_TITLE` and the expressions are
transcribed in `run3_menu_rect`, one per element, against the source line they
come from. `verify_menu.js` pins each of them, plus the non-overlap of the
whole chain, the hit tests, and that the screen actually renders.

**The one deviation** is documented at `MENU_CHAR_COLS` in `run3.c`: the
original writes the Galaxy map's y as `infinite.y + infinite.height + 30*sy`,
which collides with Play on a real stage (Play sits only `sh*0.05` below that
same row while standing ~110 px tall). The port stacks map and shop below Play,
which is the order the later build gives the same screen once its author
re-expressed it with the layout engine. Everything else is verbatim.

**The character grid** is the port's substitute for the original's single 3D
character model, so it has no counterpart to copy: it is placed in the
original's character-select slot (`y = stageHeight * 0.3`, no k — see below)
and the row below stacks from its height.

### Two traps this screen set

1. **`stageHeight * 0.3` and `stageHeight * 0.05` are stage pixels, not design
   units.** Every other number on the screen is passed through ScaledAssets'
   scale accessors (i.e. through `k`); those two are written raw
   (menu/§-__-_--__-_-§.as lines 477 and 483). Scaling them by `k` as well is a
   double scale: it compresses the whole vertical chain into the top of the box
   until the character grid lands on the title. If a menu element ever looks
   "too high", check which of the two kinds of number it is before moving it.
2. **A drawn box and its hit box must be one function.** `run3_menu_rect` is
   that function; `render_menu` draws its rects and `run3_menu_hover` tests
   them, so they cannot drift apart on a window that is not the design size.
   `verify_app.js` clicks Play by asking for its rect, not by pixel — the
   hard-coded pixel it used to use had silently started landing on a character
   box after this layout landed, and the smoke test still "passed" its
   substring check while never starting a run.

### The text face

The 2014's menu text is Comfortaa Regular — `Main.as:123` sets
`Main.<font> = Assets.getFont("font/COMFORTAA-REGULAR.TTF").fontName` and the
menu's `TextFormat` uses it at `ScaledAssets.<size>(90)`, with its text buttons
built at size 100. The port's glyph atlas (`levels/bake_font.py` →
`font_data.h`) is baked from `assets/fonts/comfortaa.ttf`, so it is **the same
face**; `menu_label` sets it at the 2014's own size (`MENU_TEXT_SIZE = 100`
design units through `k`) and `render_menu_text_w` measures the same glyphs, so
a label's box tracks both the original's anchor and its own ink.

The difference is raster resolution, not shape: the atlas is one raster
(a 39 px design cap height), drawn at `text_h / 39`. That downsamples (and
looks right) up to the base box; a window large enough to push `k` past ~1
starts upscaling it. Fixing that means a second atlas at the design size the
menu actually uses.

### Not done

* **Shop / leaderboards / edit / options are inert.** They are drawn because
  the 2014 draws them, and `run3_menu_hover` reports them, but the port has no
  view behind them (see the note in `app.js`'s menu click handler).
