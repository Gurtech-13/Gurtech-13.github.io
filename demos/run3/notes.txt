0. WHAT THIS PROJECT IS
------------------------------------------------------------------------------
A faithful web port (C -> wasm + plain JS host) of the Flash game **Run 3**.
The original game's decompiled ActionScript is the authority for everything.

  run3.h        host API (what app.js calls) + screen constants
  run3.c        simulation, game state, camera placement, level bookkeeping
  render.c      camera/projection, tube, cutscene cast+props, font, map, menu

  `TunnelSection`: `parseInt(getParam(param2,"tileWidth"), 75)`.

3. WHAT WAS JUST DONE (v0.9.2 -> v0.9.3): WORLD UNITS = ORIGINAL PIXELS
------------------------------------------------------------------------------
The user asked: "why do we have port units? use the units from the original
game." The engine had its own unit where 1 unit = 100 original world pixels.
Two conversions built on it were WRONG:

  (a) `level_tilew()` returned `BAKED_TILEW[bi] / 100.0`. BAKED_TILEW stores the
      original's own `tileWidth` VERBATIM (bake_levels.py copies `ex["tilew"]`
      from the `tileWidth-...` section param), so dividing by 100 threw the
      scale away.
  (b) levels with no explicit `tileWidth` fell back to a hand-set per-tunnel
      `baseTile` (1.00 == "100 px") instead of the original's 75. 858 of 1005
      baked levels have no explicit tileWidth, so most of the game ran 33 %
      bigger tiles than the original -> the character (whose size IS fixed in
      pixels by the spritesheet) read too small against the tunnel. This is the
      "characters are too small" complaint.

NOW: 1 engine unit == 1 original world pixel, so authored data is used verbatim.

  run3.h   DCAM 5.0->500.0, VIEW 34.0->3400.0, NEARZ -4.55->-455.0,
           GRAV 10.0->1000.0, JUMPV 5.6->560.0
  run3.c   LAND_BOB_AMP 0.030->3.0, lift 0.02->2.0, void drift 1.1->110.0,
           G.jump sentinels 0.001->0.1, STAGE_PX 0.01->1.0,
           level_tilew / level_xsec / apply_level_look use BAKED_TILEW verbatim,
           new `#define DEFAULT_TILEW 75.0` fallback, endless `G.tile` 0.70->75,
           new export `run3_tunnel_tile(int tun)` (a tunnel's own level tile),
  render.c VIEWPLANE_EPS 0.25->25.0, STAGE_PX_UNITS 0.01->1.0, sky star `0.01*st->x`
           -> `st->x`, near-clip constants x100, anim terms rescaled
           (`G.jump > 0.5`, `G.jv > 20.0`, `ssin(jump*0.03)`, `jh = jump/100`),
  space.c  planet offset 22.0->2200.0, ghost-tunnel tile now via
           `run3_tunnel_tile()`,
  levels.c the `baseTile` column of all 46 TUNNELS rows is now 75.0.

CHARACTER SIZE (gameplay) — `render.c: draw_runner` used a port-invented
"24 px tall at 360p" (48 px at 720p). It now uses the SAME rule as the cutscene
cast, `stage_sprite_h(frame_h, depth) = FOCAL * frame_h * 0.45681063122923593 /
depth`, plus a forward declaration of `stage_sprite_h`/`stage_char_h` above
`draw_runner`. The contact shadow and the dead-runner tile are sized from
`stage_char_h(depth)` instead of `H/360`. The run-cycle bounce is now
`spriteH * 0.03`.

MEASURED EFFECT (probe, now deleted): runner is 91.7 px tall at 720p on
Primary (was 48), 12.7 % of screen height. Character-to-tile ratio is now the
original's `0.4568 * frame.h / tileWidth`.

EVIDENCE: a pure unit change must not move a screen pixel, so the whole 11-suite
battery is the proof — all pass. Two unit-dependent assertions in
`verify_stage.js` were restated in px (endZ shot 800.0, dolly 80.0, one-unit shot
100.0, `PX_UNITS` 1.0) and the staged-pan check's absolute 1e-6 tolerance became
RELATIVE, because the port's own `ssin`/`scos` are approximations (~1.5e-7) and
an absolute tolerance on a now-100x-larger value was measuring the trig error.

Docs updated: `camera-spec.md` gained a new "## 11. World units" section with the
full before/after table; `DEOBFUSCATION.md` has the readable-src rename layers.

STILL NOT SWEPT: I did not re-audit every last literal for unit dependence. A
rescan (grep for small double literals passed to `proj`/`sproj`/`fill_quad`,
`cam_back`, `view_z`, `near_z`, `rtile`) is a cheap, worthwhile follow-up.

5. GOTCHAS, LANDMINES, AND USEFUL RECIPES
------------------------------------------------------------------------------
* The port's sprite atlas ORDER is fixed by the baked `levels/char_*.h` +
  `assets_data.h` tables (CHAR_COUNT 17, `char_frame_data[]`, `anim_ranges[]`).
  Reordering characters means re-running `python levels/bake_assets.py` after
  editing its `CHARS` list, then remapping everything that carries a char id
  (save.char, custom_cutscenes.js casts, run3.c's five stat tables).
  `anim_set` 'A' = runner/skater/child, 'B' = everyone else (different frame
  ranges — see the header comment in bake_assets.py).
* Regenerating baked data requires the asset files under demos/run3/assets/
  and, for cutscenes, the SWF zip. `bake_levels.py` prints per-tunnel counts;
  `bake_map.py` prints MAP_TUNNEL_COUNT. After any bake, re-run the suites.
* `run3.c` stat tables are indexed by the PORT's atlas id, NOT by the original's
  character id. The comments in the tables name the character, so use them.
* `verify_stage.js` encodes some unit-dependent expectations (now in px). If you
  change a unit again, expect to restate them.
* The port's `ssin`/`scos` are approximations (~1.5e-7). Never compare their
  output to `Math.sin` with an absolute tolerance on a large value.
* Cutscene cast ids in `cutscenes.js` are baked numeric ids (see
  `bake_cutscenes.py` `CHARIDS` / `OBF_CHAR`). `OBF_CHAR` maps the original's
  obfuscated actor vars to character ids per scene and was derived from dialogue
  roles + staging — do not "correct" it without evidence.
* `demos/run3/readable_src/` is untracked and regenerable; never hand-edit it.
* Do not run `git commit`/`git push` unless the user asks.

RECIPES THAT WORKED
* Deobfuscation: extend `make_readable.py`'s rename maps (class-level tokens can
  be renamed globally; member tokens must be pinned to their declaring file),
  then `python make_readable.py`, then read `readable_src/...`.
* Extracting flow-obfuscated constants: the compiler emits `X *= k` as
  `§§push(§§findproperty(X)); §§push(X); §§push(§§pop() * k); §§pop().X =
  §§pop();` with possible `if(_locN_)` junk in between — a tolerant regex over a
  ~260-char window before `pop().X = pop();` recovers them (this is how the stat
  table above was checked).
* The 11 `verify_*.js` suites boot the real wasm and drive real frames; they are
  the fastest way to prove a change did not move the picture.

7. STAGED CUTSCENE CAMERA - measured, do not re-litigate from theory
------------------------------------------------------------------------------
The staged frame's cross-section gauge is PI/2 and the camera's pan conversion
is its inverse, (x,y) -> (y,-x). Both were re-derived this session and both
have to move together:

  run3.c   run3_stage_pos_x() =  g_stageY * STAGE_PX
           run3_stage_pos_y() = -g_stageX * STAGE_PX
  render.c #define STAGE_GAUGE (PI / 2.0)

A PI gauge + (x,y) -> (-x,-y) was tried and REVERTED: render.c's own comment
claimed PI put the port's floor at the screen bottom, but the port's side 0 is
not the original's side 0. verify_stage.js's cross-section assertion is the
lock, and it fails under PI: at PI it reports "side 0 is not to the right of
the axis (0,106)". Under PI/2 it passes with
"side 0 at (+107,0), a quarter turn DOWN to side 4 at (0,106)" - i.e. the
port's ring index IS the original's side index (which is what makes
`placeAt(ring,row)` land a cutscene actor on the wall the scene named).

Do NOT clamp or zero the authored pan. Measured on ComingThrough (tun 0,
lvl 9, authored camera setPosition(2,106,4129), zb 0):
  dist = 228.5 px, staged pos = (106,-2,-228.5)
  the scene's own cast (frame 1: ring 4 z 1.9, ring 4.5 z 1.0) lands at
    bbox x[600,718] y[442,537], centre (659,490)
  the bore axis lands at (636,186), the tunnel radius reading 281 px at that
    depth
So the cast sits centre-BOTTOM (upright) and the axis in the upper third; the
pan is the composition - the camera is ~55% of the way out toward the wall the
cast stands on, which is what keeps the crew in frame. Zeroing it (an axis-
centred viewpoint) pushes the cast to the screen's right edge and, at these
ratios, can throw other scenes' casts out of frame outright.

APPLIED (0.9.5, at the user's request, two changes, nothing else):
  a) "the centre pixel must be the tunnel axis" - solved with an OFFSET, not
     by dropping the pan. The pan offset is calibrated on ComingThrough's own
     authored frame: run3.c's STAGE_PAN_X 2.0 / STAGE_PAN_Y 106.0 (that scene
     sets the camera to (2,106)), subtracted in the ORIGINAL's frame before
     the gauge turn. Every scene keeps its own authored pan relative to that
     rig. Measured after the change: ComingThrough's staged pos is
     (0.0,0.0,-228.5), the bore axis lands at (639.5,360.0) against a frame
     centre of (640,360) - dead centre, 0.5px off.
  b) "flip the scene upside down" - the half turn in the gauge, i.e. a genuine
     180-degree ROTATION of the picture, not a mirror. render.c's STAGE_GAUGE
     is now PI/2 + PI and run3.c's pan inverse is the matching (x,y)->(-y,x).
     The quarter turn + half turn is locked by verify_stage.js:
       staged cross-section OK (side 0 at (-106,0), a quarter turn UP to side 4
       at (0,-107); a clean 180-degree rollout, both radii 106px)
     (the same probe read (+107,0) / (0,106) before, so the rollout is exact).
     ComingThrough's cast moved from centre-bottom (659,490) to the frame top
     (616,50) - the scene is presented a half turn from the cross-section
     gauge. If a screenshot says the half turn should go the other way (or
     should be a mirror), it is a one-line sign change in STAGE_GAUGE plus its
     matching inverse - but the two MUST move together.

The shot distance is NOT clamped: negative distances are legitimate (the
camera is simply on the far side), and clamping them would break BoatRide /
GrandOpening / SocraticMethod, which is exactly what the user objected to.
The pan is NOT clamped either. Known remaining gap, not touched: a staged
frame's `view_roll` (render.c) is only set on the gameplay path, so the sky
sphere and the space layers do NOT take the staged frame's roll - they were
already stale under the old gauge, and the half turn does not change that.

7b. WHY THE 0.9.4/0.9.5 CAMERA WORK WAS INVISIBLE (fixed in 0.9.6)
------------------------------------------------------------------------------
`bake_cutscenes.py` writes `ca` ONCE PER SCENE, on the timeline object
(`tl[c] = {"ca": c in shots, ...}`, line 314). Segments are
`{f, cam, actors, props}` - they have no `ca` of their own (verify_stage.js
line 328 reads `tl.ca`, confirming the intended model).

`app.js`'s `stageGoto` decided authored-vs-legacy with `if (s.ca ||
stage.cams)` - i.e. it read the flag off the SEGMENT. Measured over the baked
data: 32 scenes have a timeline, 25 are `tl.ca===true` (219 authored segments),
and **0 segments carry their own `ca`**. So every authored scene silently took
the legacy side/lift branch. The bake's real camera values were then fed to
`run3_stage_cam` as NORMALISED side/lift and clamped to [-1,1]:
ComingThrough's `setPosition(2, 106, 4129)` became side=1, lift=1 - the camera
parked off the wall in a corner (the "top left" framing), `g_stageAuthored`
was never set, `stage_gauged` stayed 0 (no 180-degree rollout), and the
authored shot distance was never used either.

Fix: `stageOpen` computes `stage.authored = baked ? !!meta.ca : false` and
`stageGoto` tests `stage.authored || s.ca || stage.cams`. Measured on a real
staged frame afterwards (ComingThrough, 1280x720):

  gauge      4.712389   (PI/2 + PI: the half-turn rollout is live)
  engPos     (0.00, 0.00, -228.5)   (camera exactly on the bore axis)
  bore axis on screen  (639.5, 360.0)   vs centre (640, 360)
  side 4 cy 12.5, side 12 cy 707.0  ->  4 ABOVE 12: the frame is rolled 180

BARE-LITERAL CAMERA Z (same round). 215 of the 219 authored segments carry
`zb = 0`, the bare-literal form, which the run3.c docstring already described
as unresolvable (its origin is the scene's own section chain; the cast's rows
are level-local). Read as a distance it lands anywhere from -12948 to +6375 px
across the baked scenes - only 68 of 215 land inside the original's 15..3000
near/far band. `stage_shot_dist` was ignoring that and returning the raw value,
which staged most scenes with the cast BEHIND the camera (OfCourse resolved to
-9739 px and verify_app's gate frame drew an empty shot). It now believes the
bare form only inside the band and otherwise falls back to `stage_own_dist()`
(one apothem, `CAM_BACK_STAGE`). The authored PAN, quaternion and gauge are
unaffected - this decides the DISTANCE only, and the 4 `zb=1` endZ segments
still resolve exactly.

Still open from this round: 32 of the 64 voiced scenes have no gallery icon
(`assets/cutscenes/<name>.png`), so `openGallery` fires 32 404s; `img.onerror`
hides them and locked cells read "???" anyway, so it is console noise only.
