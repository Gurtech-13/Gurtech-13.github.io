Java-based Scratch-like web application with Python block support.

JavaScriptupdated 2025-06-02

Project Description

This project is a web application that provides a simplified, Scratch-like visual programming environment. Users can drag and drop blocks (including custom Python code blocks) into an assembly area to create simple programs. The frontend is built with HTML, CSS, and vanilla JavaScript, while the backend is a lightweight Java HTTP server responsible for executing the programs. Python code blocks are executed using an embedded Jython interpreter.

The primary goal is to explore the integration of a visual block metaphor with Python scripting, executed server-side, and to build a foundation for more complex block-based programming.

Features (Current State)

  • Web-based interface: accessible via a modern web browser with a tabbed interface ("Scripts", "Costumes", "Sounds").
  • Basic sprite system:
    • A default "Sprite1" is created on application startup (both client- and server-side conceptual model).
    • Scripts, costumes, and sounds are managed in the context of this active sprite.
    • A "Sprites" panel displays the list of sprites (currently just "Sprite1") and allows selection.
  • Visual stage: a 480×360 pixel stage where sprites are rendered. Sprites display their current costume at their X, Y coordinates ((0,0) is center, Y positive is up, similar to Scratch).
  • Scripts tab:
    • Three-panel layout: block palette, script assembly area, and stage area (text output).
    • Drag-and-drop: blocks can be dragged from the palette to the assembly area for the active sprite, allowing vertical stacking.
    • Block configuration & types:
      • Python code block: opens a modal for Python code input; executed server-side using the embedded Jython interpreter.
      • Say block (Looks): prompts for text; the server simulates a "say" action with output in the stage.
      • Loop block (Control): prompts for a count; rendered with a visual placeholder for nested blocks (execution of children not yet implemented).
      • Go to X:Y: block (Motion): prompts for X and Y coordinates; affects the active sprite's position on the stage.
      • Switch to costume block (Looks): prompts with the active sprite's available costumes; changes the sprite's appearance.
    • Multi-block script execution: the frontend sends a JSON array of the active sprite's blocks to the server, which parses and executes them sequentially.
    • Aggregated text output: output from all executed blocks is displayed in the stage area's text output section.
  • Basic variable system: create global or sprite-local variables via a UI dialog (name, scope).
  • Variable blocks: "Set [Variable] to [Value]" and "Change [Variable] by [Value]" blocks.
  • Variable reporters: created variables appear as draggable reporter blocks in a "Variables" palette category.
  • Stage monitors: variables can be toggled for display on the stage, showing name and current value; monitors update optimistically during script execution.
  • Costumes tab (per sprite): select local image files for the active sprite; thumbnails are shown and clicking one sets it as the current costume.
  • Sounds tab (per sprite): select local audio files; sounds are listed with a "Play" button for in-browser playback.
  • Server-side operations: Java HTTP server for static files and API requests, with server-side logging (server.log).
  • Basic script runner (legacy): retains a /run/<script_name> endpoint.

Directory Structure

  • src/main/java/com/example/SimpleHttpServer.java — core Java backend code, including request handlers.
  • src/main/java/com/example/JythonExecutor.java — executes Python code using the embedded Jython interpreter.
  • webapp/ — all frontend files (index.html, style.css, js/app.js).
  • scripts/ — example shell scripts for the legacy /run/ endpoint.
  • lib/ — directory for JAR dependencies. You must create this directory and place the required JARs (Jython Standalone and Org.JSON) here.
  • server.log — log file generated by the Java server.
  • out/ (optional, created during build) — default directory for compiled Java class files.
  • DESIGN_NOTES.md — conceptual details about program execution architecture and sandboxing.

Prerequisites

  • Java JDK 8 or higher to compile and run the server.
  • Jython Standalone JAR to execute Python blocks from the web UI.
  • Org.JSON JAR for parsing JSON sent from the frontend.
  • Python 3 interpreter (optional, legacy script runner only) for the /run/<script_name> endpoint; must be on the system PATH. Not used for Python blocks added via the UI.
  • Web browser to access the application.

Dependency setup (lib/ directory)

  1. Create the lib directory in the project root if it doesn't exist.
  2. Download the Jython Standalone JAR from the Jython official website (e.g. jython-standalone-2.7.3.jar) and place it in lib/.
  3. Download the Org.JSON JAR from Maven Central (e.g. json-20231013.jar) and place it in lib/.

After setup, lib/ should contain at least jython-standalone-X.Y.Z.jar and json-YYYYMMDD.jar.

How to Build and Run

  1. Ensure lib/ and the Jython & JSON JARs are set up as described above (adjust version numbers as needed).
  2. Compile the Java server from the project root (create out first with mkdir -p out):

    Linux/macOS (colon classpath separator):

    javac -cp "lib/jython-standalone-2.7.3.jar:lib/json-20231013.jar" -d out src/main/java/com/example/*.java

    Windows (semicolon classpath separator):

    javac -cp "lib\jython-standalone-2.7.3.jar;lib\json-20231013.jar" -d out src\main\java\com\example\*.java

    The server will not function correctly without these JARs and the correct classpath setup.

  3. Run the server:

    Linux/macOS:

    java -cp "lib/jython-standalone-2.7.3.jar:lib/json-20231013.jar:out" com.example.SimpleHttpServer

    Windows:

    java -cp "lib\jython-standalone-2.7.3.jar;lib\json-20231013.jar;out" com.example.SimpleHttpServer

    The server starts on port 8000 and logs to the console and server.log.

  4. Access the application at http://localhost:8000/.

How to Use (Current Functionality)

  1. Open the application. The "Scripts" tab is active by default and a default "Sprite1" is created and selected.
  2. All blocks added, costumes uploaded, and sounds uploaded apply to the currently active sprite.
  3. Adding blocks: drag blocks from the block palette to the script assembly area. Each block type prompts for its configuration (Python code, text to say, loop count, X/Y coordinates, costume name).
  4. Running: click "Run Program" to send the active sprite's stacked blocks to the server for sequential execution. Text output appears below the stage; visual changes (position, costume) happen on the stage.
  5. Variables: click "Make a Variable" in the Variables category, enter a name (letters, numbers, underscores; must start with a letter or underscore), and choose scope ("For all sprites" or "For this sprite only"). Reporters appear in the palette (locals prefixed with the sprite name, e.g. Sprite1:myLocalVar). Checkboxes toggle stage monitors. "Set/Change Variable" blocks prompt for the variable and value. Non-numeric current values are treated as 0 before a change; unknown variables are created at 0.
  6. Costumes: use "Choose Files" to add local images; clicking a thumbnail sets the active sprite's costume.
  7. Sounds: use "Choose Files" to add local audio; each sound has a "Play" button.

Testing

Automated JavaScript UI testing (e.g. with Jest) was explored, but was not feasible in the current execution environment (no Node package installation or test runners). Manual testing is the current approach; detailed manual test cases live in TESTING.md.

Known Issues & Limitations

  • Backend execution of "Go to X:Y:" and "Switch to costume" targets a hardcoded sprite1; true multi-sprite execution context is not yet implemented.
  • Sprite position/costume changes are optimistic on the frontend; the server does not yet send back authoritative full state.
  • Only one default "Sprite1" exists; there is no UI to add, delete, or rename sprites.
  • Costumes and sounds are client-side only (Data URLs in JS arrays) and are lost on refresh.
  • Blocks can only be appended to a script; reordering or deleting is not implemented.
  • The Loop block has a visual placeholder, but nesting/executing child blocks is not functional.
  • Configured blocks cannot be edited after placement.
  • Variable reporters cannot yet be dragged into other blocks' input slots — prompts accept literal values only.
  • Stage monitors reflect optimistic updates; no full variable state is returned after execution.
  • No state persistence: all project state is lost on page refresh.

Future Ideas

  • Execute child blocks within Loop blocks.
  • Edit and delete blocks in the assembly area.
  • Drag-and-drop reordering of assembled blocks.
  • More standard blocks (variables, math, conditionals).
  • Visual feedback for block connections.
  • Save and load user-created programs.

Design and Architecture

The current execution model uses a JSON array payload (a sequence of blocks) sent to the /api/execute_program endpoint. Python blocks run via Jython inside the Java server; standard blocks like "Say" are handled by Java logic. The backend iterates over the array to process blocks. A more Scratch-like execution architecture (nested loop execution, block type handling, state management, sandboxing) is planned — see DESIGN_NOTES.md.
